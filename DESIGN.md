# DESIGN.md — how VI is built, and why

VI is a vi-style text editor for CP/M 2.2 on an Intel 8080. It ships as one
file, `VI.COM`, and edits files larger than memory by paging them through a
single windowed gap buffer. vim 9.1 is the reference for behaviour: a command
is done when it matches vim on files from 0 to 100 K, and every place it does
not match is written down.

This file covers the design as a whole: the layers, the memory map, the rules
each part depends on, and how the editor is built and tested. It links to the
detailed documents instead of repeating them:

| Document | What it holds |
|---|---|
| `COMMANDS.md` | every command, its status, and each deviation from vim |
| `RENDER.md` | the VT100 renderer: placement, render intents, paints, message row |
| `BUFFER.md` | the gap buffer, the pointer row, paging, the logical-offset API |
| `VI.DOC` | the user manual as it reads under CP/M `TYPE` (generated by `build_doc.py`) |
| `run_tests.py` docstring | which test battery to run for which change |

---

## 1. The constraints everything follows from

These are facts about the machine, not preferences. Most decisions below trace
back to one of them.

- **An 8080 in a 56 K TPA.** No Z80 instructions. The editing arena is the RAM
  between the top of the program and 7 pages below the BDOS
  (`BUFEND = [0006H] - 700H - 1`, WM `INIT`). **Every byte of the image comes out of
  the arena**, so the binary is the scarce resource. Commands are priced in
  bytes before they are built, and a command that earns too little gets cut.
- **The console is a 9600-baud serial line**, about 960 characters a second. A
  23-row repaint of 56-column text is ~1450 characters, which takes 1.5 s. The
  8080's own work at 2 MHz is small by comparison, so **how fast the editor
  feels depends on how few characters it sends.** The renderer is designed
  around that (§6), and `paintcost.py` measures it.
- **CP/M 2.2 file I/O**: 128-byte records, no byte length (the last record ends
  at a `^Z` or at its 128th byte), BDOS directory operations that scan the
  whole directory, and a BDOS entry at `0005H`.
- **The CCP** puts the first command-line token into the FCB at `005CH` and
  leaves the rest of the tail at `0080H`. That tail is also the default DMA
  buffer, so the first disk read overwrites it.
- **Microsoft M80/L80**:
  - Only the first 6 characters of a name are significant.
  - L80's command line must fit CP/M's ~127-character console line.
  - L80 fills `DS` space with whatever was in its own memory, not zeros.
  - An unresolved external is bound to `0000H` (warm boot) with only a warning.

## 2. Layers and link order

Six code modules plus a reserve block, linked in this order:

    L80 VI,SCRN,CMD,KEY,PAGE,BUF,RSV,VI/Y/N/E

| Module | Role | Origin |
|---|---|---|
| `VI.MAC` | entry at `0100H`: read the command tail, open the file, then the loop *key → dispatch → paint* | VI |
| `SCRN.MAC` | BIOS-direct console output, geometry probe, placement (`LAYOUT`), all painting, the message row | VI (placement follows WordMaster's model) |
| `CMD.MAC` | the vi layer: key tables, dispatch (`CMDDIS`), motions, operators, insert/replace, ex line, `.`, marks, search sweep, command-line switches | VI |
| `KEY.MAC` | VT100 key decoder and the type-ahead ring | VI (the ring is WordMaster's mechanism) |
| `PAGE.MAC` | files and paging: record engine, load, spill/rewind, save and rename | WordMaster 5.55A, verbatim, plus appended glue |
| `BUF.MAC` | the gap buffer: pointer row, insert/delete/move, line moves, matcher, Q-buffer | WordMaster 5.55A, verbatim, plus the logical-offset API and undo capture |
| `RSV.MAC` | emits no bytes; names the storage above the image | VI |

**Link order is load-bearing.** `VI` links first so `START` sits at the TPA
base. `RSV` links last and emits nothing, so its base is the top of the image.
`BUF` links just before it, and its `PBEGMEM` (the arena base) is `RSVTOP`.

**`VI.INC`** holds the equates shared by the VI-written modules: ASCII, BDOS,
render intents, editor modes, message codes, and the buffer sizes RSV.MAC
shares with the modules that use them. `BUF.MAC` and `PAGE.MAC` do not include
it; they keep WordMaster's own local constants.

## 3. WordMaster's engine, verbatim

`BUF.MAC` and `PAGE.MAC` are a transcription of MicroPro WordMaster 5.55A's gap
buffer and pager, from the `WM.ASM` disassembly. That source is kept outside this
repo. The transcription is instruction for instruction, the same object code. The
only change is that WM.ASM's address labels (`Lxxxx`) are renamed to
descriptive names. Every routine cites its `WM.ASM` line, so the files still
diff against the source.

**Why verbatim.** WordMaster's paging (spill the head to a work file, rewind
it, read ahead, save by renaming) is a shipped design that handles files much
larger than RAM. Transcribing it exactly means it can be checked line by line
against `WM.ASM` and proven byte-exact by the buffer gate (§9). An adapted copy
could only be checked against itself. The vi layer is free to differ from
WordMaster. The engine changes only for a stated reason.

**Where it differs from WordMaster.** Each difference is flagged at its site:

- `ERRMSG`'s tail, and `FATAL` entering it: WordMaster jumps back to its own
  command loop, which does not exist here. They print the message, set `ERRFLG`
  and warm-boot.
- WordMaster's `GETKEY` is replaced by `KBPOLL` (KEY.MAC) in `RDSEC` and
  `POLLBRK`, so the long engine loops drain type-ahead into VI's ring.
- `OPENFIL`/`SAVEFIL` wrap WordMaster's inline open and `ENDEDIT` sequences as
  callable routines. They keep one drive and user 0.
- **A WordMaster bug fix in `FILLBUF`.** WordMaster stores the last record's byte
  count only when it finds a `^Z`. A file that ends exactly on a record boundary
  without one left the count at 0. `PAGEBOT` then stepped the source back without
  removing the record from the buffer, so paging to the bottom, back to the top
  and saving wrote that record twice. `FILLBUF` now stores 80H for a full
  record.
- `SECBUF` has a guard byte on each side, because `STAGSEC` writes one byte past
  each end.
- The backup work file is `VIBACKUP.$$$`, where WordMaster names it
  `WMBACKUP.$$$` (`BAKNAM`). The name is the same length, so nothing moves.
- `INSSTR` takes the string pointer in `DE` rather than hard-wiring WordMaster's
  single `SRCHBUF`, because `:s` keeps its replacement in its own buffer. The
  length-prefixed layout is still WordMaster's.

**Added, not WordMaster** (tagged in the source):

- **The logical-offset API** (`CUROFF`, `LOGLEN`, `CHARAT`, `GOTO`, `DELFWD`,
  `DELPRV`). A logical offset is an index into the resident text as if the gap
  were absent. The vi layer works only in logical offsets, and the gap pointers
  stay private to BUF.MAC. See `BUFFER.md` §7.
- **`LNDLT`**, the signed number of lines the cursor crossed since the last
  frame. `GOTO` and `DELPRV` keep it, and placement (§6) depends on it.
- **The write path.** `WRTO`, `DISCRD` and `CNTLF` handle `:w {file}` and `:e`;
  `REOPEN` and `SEEKTO` let `:w` keep editing at the same line, row and column.
  They are built only from WordMaster primitives (`SAVCLO`, `RENAME`, `RENF`,
  `DELF`, `MAKEF`, `RDNEXT`). `SAVEFIL` (WordMaster's `ENDEDIT`) can only write
  back the file it read, so the editor does not call it. It stays because the
  four pager tests use it as their save step, which is what tests WordMaster's
  own save side.
- **Undo capture** in the primitives (§5).

**Layout contracts inherited from WordMaster**, which code relies on and which a
move would break:

- `AUXCNT` sits directly after `NEWFIL`, because `GOLINE` reads the byte after
  `NEWFIL` as `AUXCNT`'s low byte.
- The three FCBs carry open flags at FCB-1 and FCB-2, and those neighbours must
  stay `DB 0`.
- `SRCHST` and `SREPL` are read through `[DE-1]` for their length.
- `005BH`, the source's has-data flag, is cleared before every open, as WM's
  `L02F2` does. Otherwise a file that does not exist would be read from
  whatever the last program left there.

## 4. Memory map

    0100H   VI.COM image: VI SCRN CMD KEY PAGE BUF (code + initialised data)
    RSVBAS  the reserve block (RSV.MAC): stack, '.' buffers, ex line, file name,
            type-ahead ring, sector stage + guards, undo records, marks
    RSVTOP  = PBEGMEM: the arena base
              pointer row, text + gap, Q-buffer (the yank register), undo region
    BUFEND  = BDOS base - 700H - 1

In this build: the image is 16160 bytes, the `.COM` file 16256 bytes (127
records), the reserve block 791 bytes (`4020H`–`4337H`), and the stack 128
bytes.

**Why a reserve block.** L80 writes every byte up to the top of the image into
the `.COM`, `DS` included, and fills that space with its own leftovers rather
than zeros. A `DS` inside the image therefore adds file bytes and load time for
storage that is overwritten before it is read. RSV.MAC names that storage
above the image instead. Only a `DS` that is written before it is read may
move there. One that sits against an initialised neighbour it depends on (§3)
stays put. `build_vi.py` checks each `;CHECK` line in RSV.MAC against BUF.MAC's
equates on every build, because a reserve that silently comes up short would
overrun into the arena. **Nothing may assume a `DS` starts at zero.**

**The stack is 128 bytes** because `.` replays keys through `CMDDIS` from inside
a handler, which adds a level of nesting.

**Labels are unique in their first six characters**, internal ones included.
Because L80's padding holds its own symbol-table leftovers, renaming a label
changes bytes in `VI.COM` without changing any code. Prove such a change with
the tests, not with a checksum.

## 5. The vi layer (`CMD.MAC`)

**One dispatch point.** Every key goes through `CMDDIS`, whether it comes from
the keyboard, from `.`, from the `+{n}` switch, or from the headless test
harnesses. Commands are table rows:

- `CMDTAB`: command-mode keys
- `ACTTAB`: decoded arrow and function keys
- `EXTAB`: ex commands
- `OPCTAB`: the motion class for each key an operator accepts

`VSCANQ` serves the two top-level tables. It treats a missing key as "nothing
drawn, nothing moved", so an unknown key costs a cursor move instead of a
repaint.

**Two table invariants** a search for label names cannot see:

- **Every key in `OPCTAB` must also be a `CMDTAB` row.** Otherwise `OPPEND` takes
  the class, the motion does nothing, and class 1's inclusive widening turns the
  empty span into a one-character delete.
- **`cw` is vi's `ce`.** `OPPEND` rewrites the pending key (`SUI 'w'-'e'`) and
  dispatches the result, so `CMDTAB` rows are reached by computed key. The `e`
  row cannot be removed even though nothing names its handler.

**Operators** measure a span around any `CMDTAB` motion. There are four classes:

| Class | Kind | Operators |
|---|---|---|
| 0 | charwise exclusive | `d`, `c` |
| 1 | charwise inclusive | `d`, `c` |
| 2 | linewise | `d`, `y` |
| 3 | charwise exclusive jump (`` ` ``) | `d`, `c` |

- `c` refuses class 2 because it has no empty line to open an insert on. `cc`
  does nothing.
- `y` takes only class 2 because there is no charwise register.
- A span that takes no line break asks for a one-row repaint.

**The yank register is WordMaster's Q-buffer.** It is a second gap buffer inside
the arena, part of the pointer row, so it slides with the gap and grows through
the same `MKGAP` machinery as the text. Its limit is the arena less `RESVMEM`,
about 27 K. WordMaster has no copy without delete:

- **`yy` deletes the lines into the register and puts them straight back.**
  `YKGO` puts nothing back when nothing was taken. Without that check, a refused
  yank would splice a stale register into the file.
- **`dd` deletes forward only**, from the start of the line, because `QCOPY`
  always reads from `GAPEND`. A backward delete cannot reach the register.

**`.` is keystroke replay.** `DOTPRE` and `DOTPOST` record the keys of the command
being typed. When that command ends and changed the text (`DOTCHG`, set by
`MARKMOD`), the keys become the recording. `.` feeds them back through
`CMDDIS`. So no command needs a second implementation to be repeatable, and a
command added later can be repeated from the day it is built. The limit is
`DOTMAX` = 128 keys.

**`u` is captured at the primitives, not in the commands.** Six primitives can
change resident text: `PUTGAP`, `QGET`, `DELFWD`, `DELPRV`, `UNDELF` and
`QPUTLN`. `INSSTR` records through `UNDINS`. Each reports what it did, so no
command can forget to record itself.

- A record holds type, offset, length and region offset.
- The bytes are kept for inserts as well as deletes, so one region replays in
  either direction, and `u` undoes `u`.
- The region grows **only at the command boundary** (`UNDBEG`) and is written
  without calling `MKGAP`. Growing it mid-command would invalidate a raw
  pointer that `DELPRV` hands to `SETGAPB`, and would overwrite the gap, where
  `R`'s backspace expects to find the byte it restores with `UNDELF`.
- Limits: `URMAX` = 24 steps and `UNDCAP` = 1024 bytes per change.
- Reach is the resident window. `PGTOPM` counts how many times the pager moved
  `TXTBEG`, the only thing that shifts logical offsets. `OUTREC` and `SRCREC`
  are not a paging signature, because `UPDMARK` raises them on every edit.
- `:w` clears the undo, because the write rebuilds every offset.

**Marks `a`–`c`** are an offset plus the `PGTOPM` at the time they were set,
stored in the reserve block. A mark is **dropped, never moved**. `MKDROP` runs
from `MARKMOD`, one 16-bit compare per mark with nothing to update, which is
why this rule was chosen over vim's. A mark is also lost to `:e` or to paging
away. `MKHOLD` holds the drop off across `yy`'s round trip.

**Search** is WordMaster's `MATCHF`/`MATCHB` swept across the whole file by
WordMaster's `FINDA` loop (`SRCHW`), paging one step per miss. The pattern is
literal (there is no room for a regex engine). Overlapping matches are found.
`?` finds the last match that *ends* before the cursor, because the bytes after
the cursor are across the gap. `:s` uses the same matcher and splices
replacements with `INSSTR`. Placement after a jump (`G`, `gg`, `+{n}`, search,
`:s`, `` ` ``) all goes through `GPLACE`.

**The command line** is `VI name [+{n}|+] [-R]`. The switches come after the
name because the CCP parses the first token into the FCB that is opened. The
tail is scanned before anything else runs, because the first sector read
overwrites it. There is no config file and no `/Ln /Cn`: `SCINIT`'s DSR probe
finds the terminal size for free, and a parser would cost about two records.

**Commands chosen or cut on size and use.** This editor is mostly used for 8080
assembly.

- `f F t T ; , %` and `^E ^Y` are not built: about 720 bytes that `/`, `^D ^U ^F
  ^B` and the other motions cover.
- A count on `i a A I o O R ~ r C D J` is ignored. It is held back for size.
- `C` is kept although `D` then `a` produces the same text, because `C` is one
  change: one `.` repeats it and one `u` restores the line. `D`+`a` is two
  changes, and with single-level undo, the text `D` removed cannot be recovered.

## 6. Rendering (`SCRN.MAC`)

Detail is in `RENDER.md`. The design decisions:

- **Placement follows WordMaster; output does not.** Placement is cursor-relative
  (`WINROW`, `LNDLT`, WM `LINPOSB`/`RGET`/`NEEDIN`, `WRLIM` raised as WM
  `MEASURE` does). A frame therefore costs one screenful of text however deep in
  the file the cursor is. WordMaster's output model assumed a fixed 80×24
  terminal with only clear, address and erase-to-end-of-line. VI probes the
  geometry at startup (24–200 rows, 80–132 columns, 24×80 fallback) and uses the
  scroll region, IL/DL, RI and ICH.
- **Render intents, no shadow buffer.** Each command sets `RINTENT` to say what it
  changed. `SCDRAW` picks the cheapest paint that is correct.
- **The default is `R_FULL`, set before every key.** A command lowers it only when
  it knows what changed. A wrong tag can then only cost an unnecessary repaint,
  never leave stale text on the screen.
- **`RINTENT` and `ILN` live in CMD, not SCRN.** The headless harnesses link CMD
  without SCRN, so a render parameter owned by SCRN would be an undefined global
  there.
- **Messages are drawn after the frame** (`MSGPST`), because a full repaint blanks
  the bottom row.
- **Long lines pan, never wrap.** Tabs are expanded before clipping.

## 7. Console input (`KEY.MAC`)

- **All console I/O goes to the BIOS directly**, through the warm-boot vector at
  `0001H`, never through the BDOS. This is the same choice as WordMaster's
  `BIOSC`.
- **Type-ahead ring**: 32 bytes, 31 usable. `KBPUMP` drains whatever the BIOS
  has waiting.
  - The engine's long loops (`GOLINE`, `RDSEC`, `POLLBRK`) call `KBPOLL`, so keys
    typed during a long operation are kept rather than lost.
  - The full repaint checks the ring between rows (`KBRDY`) and abandons the frame
    when a key is waiting. `FORCEF` makes the next frame a full one.
- **ESC sequences** (CSI and SS3 arrows, Home/End, PgUp/PgDn, Ins/Del) are decoded
  in `GETKEY`. A lone ESC is confirmed after `ESCTMO` = 500 polls.

## 8. Files on disk

- **Work files.** The pager spills to `name.$$$` and backs up to `VIBACKUP.$$$`,
  both on the file's drive.
  - `:w` on the buffer's own file keeps `name.BAK`; `:w {file}` does not.
  - A write to another drive is copied record by record; on the same drive the
    work file is renamed.
- **Line endings are stored verbatim** (CR, LF or both, as read), and the file is
  written back exactly as it was read. There is no `fixeol` (see `COMMANDS.md`).
- **Quitting deletes the work files only if one was written** (`DISCRD`,
  `WRREC`'s flag). A BDOS delete scans the whole directory, about 250 K
  instructions on the 8 MB drive. The per-FCB open flag cannot serve as the test,
  because reading the backup to its end clears it while the file still exists.

## 9. Building and testing

**Build.** `build_vi.py` drives the `altairsim` simulator over MCP (`mcpdrive.py`,
`vi.toml`):

- It copies the sources onto the tracked image `CPM22-8MB-56K-VI.DSK` with the
  host-bridge `R` utility, runs M80 and L80 there, and brings `VI.COM`, `VI.SYM`
  and the listings back with `W`.
- It builds on the committed image in place, so the image always carries the
  current sources, and `SUBMIT VI` (`VI.SUB`) rebuilds inside CP/M.
- **Disk images are never parsed or written from the host.** Every file goes in
  and out through the guest.
- Any L80 `%` diagnostic fails the build, since L80 still writes a `.COM` after
  one.
- Sources (`.MAC`, `.INC`, `.SUB`) must be CRLF, or M80 reports "No END
  statement".

**Test batteries.** `run_tests.py`'s docstring says which to run for which
change.

| Battery | What | Links |
|---|---|---|
| buffer/paging gate | `BUFTST`, `PGTST`, `PGXTST`, `PGXINS`, `PGBKTST`: the WordMaster engine alone, byte-exact round trips of files several times a shrunken ~6 KB window | test, PAGE, BUF, RSV |
| component | `MOTTST`, `CMDTST`: scripted keys through CMD headlessly | test, CMD, KEY, PAGE, BUF, RSV (no SCRN) |
| acceptance | `accept_vi.py`: the real `VI.COM` in the simulator on 0 B–109 K files, screen and saved file checked | the editor |
| smoke | `smoke_vi.py`: boot, paint, edit, save, `VI.DOC` under `TYPE` (~5 s) | the editor |
| paint cost | `paintcost.py`: characters sent per keystroke against a budget | the editor |

- **The gate binaries link only the test, PAGE, BUF and RSV.** Anything they call from
  outside that set (`CNTTST`, `CMDCNT`, `KBPOLL`) is stubbed in each harness. An
  unstubbed external would be bound to `0000H` and warm-boot mid-run, so a
  change to BUF/PAGE or to their `EXTRN`/`PUBLIC` contract requires the gate.
- **vim is the reference.** Each vim table in `accept_vi.py` is recorded from
  vim 9.1 on a 24×80 pty with `nowrap` by `vimref.py`, which can regenerate and
  re-check every row. Behaviour is recorded before a command is built.
  - `vimref.py` runs `accept_vi.py`'s definitions from its AST rather than
    importing it: importing `smoke_vi` clears the work disks under a running
    suite.
  - Under `-s` script input vim never syncs undo, so `vimref.py` forces a sync
    after each key for the `undo` and `subst` groups.
- **Parallel runs.** `fastcheck.py` runs the acceptance groups in parallel.
  Each worker gets its own simulator directory (`VI_SIMDIR`), because the host
  bridge's root is where `R` reads and `W` writes.
- **Test constants that depend on the arena are measured, not written in.**
  Every byte added to the image shrinks the arena and moves them.
- **A lone ESC sits in `GK_POLL`** waiting for the rest of a sequence. The guest
  looks idle before the key is handled, so a test must wait for the editor
  rather than read the screen mid-keystroke.
- **A comments-only change** is proven by rebuilding and comparing `VI.COM`'s
  checksum.

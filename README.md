# VI — a vi-style editor for CP/M 2.2 on the 8080

`VI.COM` is a screen editor for CP/M 2.2 that behaves like vi. It runs on a
plain 8080 in a 56 K TPA, it is 16,256 bytes, and it edits files far larger
than memory — 100 K files are ordinary — by paging text to and from disk.

vim 9.1 is the reference for behaviour. A command is not finished here until it
matches vim on files from 0 to 100 K, and every place it deliberately differs is
written down in [`COMMANDS.md`](COMMANDS.md).

```
VI                      start with an empty buffer
VI FILE.TXT             edit FILE.TXT (created on :w if it is new)
VI FILE.TXT +500        start on line 500   ('+' alone: the last line)
VI FILE.TXT -R          read only; a write needs '!'
```

The switches come *after* the file name: the CCP parses the first word of the
line into the FCB, so VI never sees it.

## What it needs

- CP/M 2.2 on an 8080 (no Z80 instructions are used)
- a VT100, or any terminal that answers `ESC [ 6 n` — the screen size is probed
- a console line; the renderer is built for 9600 baud, where a full repaint
  costs about 1.5 seconds, so it sends as few characters as it can

## What it does

Commands, with counts (`5j`, `3dd`, `20G`):

| | |
|---|---|
| move | `h j k l` `0` `^` `$` `<CR>` `w b W B e` `G` `gg` `H M L`, arrows, PgUp/PgDn |
| scroll | `^F ^B` `^D ^U` `^L` `^G` |
| insert | `i a I A` `o O` `R` `r{c}`, with BS/DEL rubbing out across lines as vim does |
| edit | `x` `dd` `D` `C` `J` `~` `u` `.` |
| operators | `d c y` over a motion: `dw dd d$ dj dG` `cw C` `yy Y y'a` |
| yank/put | `yy Y` `p P` `3p` — one register, whole lines, filled only by a yank |
| marks | `m{a-c}` `` `{a-c} `` `'{a-c}` `d'a` `` d`a `` |
| search | `/text` `?text` `n N` — a literal string, not a regex; wraps |
| substitute | `:s/old/new/` `:s//g` `:%s//g` `:2,40s//g` — literal, one undo |
| files | `:w` `:w FILE.TXT` `:e FILE.TXT` `:q` `:q!` `:wq` `:x` `ZZ` `:ve` |

The bottom row is vim's *message* line — blank until something is said on it —
not a permanent status line. `^G` says which file, its flags, and where the
cursor is. A file on another drive is named with its drive (`"B:TEST.TXT"`),
the way vim names a path outside the current directory.

Not here, on purpose: `f F t T ; ,` `%` `<< >>` `s S cc` `^E ^Y` `:100`
(use `100G`), named registers, regular expressions, `:set` and multiple
windows. Each omission is priced and argued in `COMMANDS.md` — the binary is
the scarce resource, since every byte of the image comes out of the editing
arena.

Undo is single level. There is one yank register and it holds whole lines.
There are three marks. The full list, with every deviation from vim and the
reason for it, is in [`COMMANDS.md`](COMMANDS.md); [`VI.DOC`](VI.DOC) is the
user manual as it reads under CP/M `TYPE`.

## How it is built

The editor is six assembly modules — `VI.MAC`, `SCRN.MAC`, `CMD.MAC`,
`KEY.MAC`, `PAGE.MAC`, `BUF.MAC`, plus `RSV.MAC` for the reserve block — built
with Microsoft M80/L80 **inside CP/M**, on the tracked disk image
`CPM22-8MB-56K-VI.DSK`, which carries the assembler and the host-bridge
utilities.

`build_vi.py` drives the [`altairsim`](https://github.com/deltecent/altairsim)
simulator over MCP: it copies the sources onto that image with the host bridge's
`R` utility, runs M80 and L80 there, and brings `VI.COM`, `VI.SYM` and the
listings back with `W`. Disk images are never parsed or written from the host —
every file goes in and out through the guest. `SUBMIT VI` (`VI.SUB`) does the
same build from inside CP/M.

```
python3 build_vi.py            # VI.COM
python3 build_vi.py BUFTST     # one of the test stubs
```

`altairsim` must be on `PATH`. Sources must keep CRLF line endings, or M80
reports "No END statement".

## How it is tested

Tests are written first and start red, and a command counts as built only when
the **real `VI.COM`** passes at editor level on 0 / 1-line / ~2 K / ~40 K /
100 K files — screen, cursor, window and the saved bytes all checked. Test
files include lines past the right screen edge. The vim comparison tables are
recorded from real vim 9.1 on a 24×80 pty by `vimref.py`, which can replay them
through vim again and report any row vim no longer agrees with.

```
python3 run_tests.py           # everything
python3 run_tests.py --gate    # the buffer/paging gate alone
python3 fastcheck.py           # the acceptance groups, in parallel
python3 smoke_vi.py            # boot, paint, edit, save (~5 s)
```

`run_tests.py`'s docstring says which battery to run for which change.

## Provenance

`BUF.MAC` and `PAGE.MAC` are a verbatim transcription of MicroPro **WordMaster
5.55A**'s gap buffer and its record/paging/save engine — the part that makes
editing a 100 K file on a 56 K machine possible at all. The transcription is
deliberate: the engine is kept as WordMaster wrote it, and every place it
differs is flagged at the site and listed in `DESIGN.md` §3 (including a fix for
a real WordMaster bug in `FILLBUF`). WordMaster's user interface is *not* kept —
the vi layer, the renderer and the key decoder are this project's own.
